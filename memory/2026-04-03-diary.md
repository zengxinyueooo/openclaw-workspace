## 二、素材架构升级：两张表比一张表更清醒

上午最重要的技术决策是素材双表迁移。原来 `materials` 表承担的职责太杂——采集入库、状态流转、分配查询全在一起。皮皮提出拆开：`materials` 只管入库和审核，`available_materials` 只放已过审的，是蜜蜂生图的唯一进货口。

这个设计简洁、干净。`used_by TEXT[]` 同时承担预占锁和使用记录，一个字段解决并发安全问题，不需要额外的 lock 表。239 条历史素材全部迁移，trigger 自动同步。

现在 face 有 131 条可用，nail 只有 12 条，nail-face 更是 3 条。nail 告急，但今天的采集任务 nail 全挂了——Chrome 登录态过期是最大嫌疑，待皮皮确认。

## 三、V4 生图：从 API 调用到本地工作流

今天最大的里程碑是 marketing-content-serivce 跑通。之前蜜蜂生图是通过 API 调用后端服务，现在改成本地直接跑 `ai_aesthetic_workflow`，Gemini 做审美仲裁。

跑通的关键是两件事：
1. `mosaic.py` 里有一处硬编码的本机 macOS 路径，沙箱直接崩。改成 `pathlib` 动态解析后就好了。
2. 默认 AIGC Bearer Token 在沙箱无效，皮皮提供有效 token 后跑通，审美评分 0.78，全流程 207 秒。

`run_v4.py` 写出来后，`generate.py` 和旧的 `SKILL.md` 全部清掉，Skill 文件只留一个入口，路径统一。今晚还修了审核页风格参考图缺失的 bug——根因是 `run_v4.py` 没写 `generation_tasks`，导致页面查不到 `style_url`。修复方案：生图成功后先 insert 一条 `generation_tasks`，拿到 `task_id` 再写 `generated_images`。

## 四、蜜蜂中毒事件：失控的重试和轮询

下午发现蜜蜂 token 消耗爆了 1,030k。追查下来根因是：Gemini 后端故障，生图 API 持续返回 0 张图；脚本有 4 轮重试每轮 600 秒超时；`process(poll)` 每 30 秒一次；cron 并行 spawn 了 5 个 subagent。五件事叠在一起，token 像水一样流掉了。

处置：直接改 `sessions.json` 标记 subagent 为 aborted，kill 残余 curl 进程。

这件事让我意识到，**重试策略不是「越多越保险」，是「越精准越可靠」**。失败 2 轮就应该熔断，第一个 subagent 报 0 图就应该停掉剩余的。这些改动还在待办里，下次蜜蜂上线前必须补上。
