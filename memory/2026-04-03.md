## 上午 - 素材双表架构迁移（materials → available_materials）

### 背景
皮皮提出素材管理要拆成两张表：
- `materials`：原始入库、状态流转（pending/approved/rejected），松鼠采集写入
- `available_materials`：只放 approved 素材，是松鼠分配和蜜蜂查素材的唯一入口

### 数据库变更（皮皮已在 Supabase 执行）
1. `available_materials` 去掉 `assigned_to_persona` 字段（不再需要）
2. 用 `used_by TEXT[]` 同时承担预占锁 + 使用记录（一图一用，空数组=可用）
3. 建 trigger `trg_sync_approved_materials`：materials 变 approved 时自动同步到 available_materials
4. 存量补同步：239 条 approved 素材全部进入 available_materials
5. 历史已分配素材（121 条 `assigned_to_persona` 非空）同步到 available_materials.used_by

### 当前 available_materials 可用素材数量
- face: 131 条
- nail: 12 条（偏少，需补采）
- nail-face: 3 条（偏少，需补采）

### 代码变更
| 文件 | 改动 |
|------|------|
| 松鼠 `AGENTS.md` | 查素材改查 available_materials，按 category 分桶，原子 PATCH 占用（带 used_by=eq.{} 条件） |
| 蜜蜂 `AGENTS.md` | 查素材 image_url 改查 available_materials |
| `generate.py` | 查素材、随机兜底、占用标记全部改为 available_materials + used_by |

### 核心设计决策
- **一图一用**：used_by 非空即代表已占用，查询过滤 `used_by=eq.{}`

- **tags 精细过滤**：预留在查询层，未来加 `tags=cs.{<tag>}` 参数
- 内存随机打乱只是候选顺序，真正去重靠数据库原子写

## 下午 - 蜜蜂 token 消耗过高排查

### 问题
蜜蜂 sessions 总 token 消耗超过 1,030k，皮皮发现后要求排查。

### 根因
1. **生图 API（aiAesthetic）持续返回 0 张图片**：Google/Gemini 后端故障，每次调用返回空结果
2. **脚本内有 4 轮重试，单轮 600s 超时**：每个 subagent 跑 20+ 分钟才判定失败
3. **等待期间 process(poll) 轮询频繁**：每 30 秒一次，产生大量 token 消耗
4. **cron 一次并行 spawn 5 个 subagent**：5 个都失败，token 叠加
5. **cron 触发频率偏高**：产生了 15 个 cron run session（`ralph-loop-bee`）

### 蜜蜂 subagent 强制停止
- 通过修改 `sessions.json` 将活跃 subagent 标记 `abortedLastRun=true`
- kill 了残余生图 curl 进程（PID 265846、265847、265848）

### 建议修复方向（待实施）
- 生图失败 2 轮后熔断，不等满 4 轮
- 第一个 subagent 回报 0 图时停止 spawn 剩余
- 用 `exec(yieldMs=30000)` 替代 `process(poll)` 减少 token
- 降低 cron 触发频率
