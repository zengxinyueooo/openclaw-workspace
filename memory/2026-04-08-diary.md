## nail 采集链路：从"勉强跑通"到"质量可信"

### 图片质量问题根治

上午确认了昨天发现的图片质量 bug 根因：小红书是 SPA，`Page.navigate` 跳不进详情页，`goto("/explore/xxx")` 始终停在首页，所以"进详情页取多图"的思路从根上就行不通。绕了一圈，最终发现搜索结果封面图本身就是高质量的代表图——直接用封面，不进详情页，反而更干净。

这个教训值得记：CDP + SPA 网站，不要想当然以为 `Page.navigate` 能跳子路由。

### 打标签接入，但异步化处理

下午把 ZHIPU GLM-4V-Flash 打标接入 nail/face 两条链路。跑了一轮发现每张图多 2~5 秒打标时间，30 张合计超时截断。当场把打标逻辑拆出去——新建 `tag_materials.py` 独立补标，采集主流程不等打标。

异步化是对的选择。采集和打标是两件事，不应该串联。

## face 采集：风控是真正的天花板

晚上尝试把搜索逻辑从 DOM 抓卡片改成调 edith API，理论上更稳定、更结构化。结果触发了小红书账号风控（300011），两次测试全部 0 入库。

皮皮重新登录后，风控状态未知。

这让我意识到一个更深层的问题：nail 和 face 连续跑 16 次搜索，本身就在触发风控。nail + face 之间加 5 分钟间隔只是临时补丁，长期应该是两个独立 cron，彻底隔开。

旧版走 mcporter API 不触发风控，新版浏览器模拟容易被认出来——这是架构层面的差异，不是参数调调就能解决的。

## 蜜蜂：300 张图，但椰椰椰即是个漏洞

蜜蜂今天产出 300 张图，成功率 64%，整体还行。但椰椰椰即 6 次全部 `api_empty`，从早到晚没变，说明是这个账号的素材/参考图组合与 Gemini 不兼容——特定输入稳定 0 产出，不是偶发失败。

这类"稳定失败"比随机失败更危险，因为它会一直消耗配额、占用 cron 时段，却永远没产出。需要尽快排查是 portrait_url 还是 style_url 的问题，换一张参考图试试。

## 蚂蚁：修了一个悄悄翻车的 bug

先叫Momo 笔记发出去之后，皮皮发现正文和标签跟审核时改的不一样。翻下来是蚂蚁创建资产时用了 `candidate_contents[0]` 而不是人工改过的 `content` 字段——候选值覆盖了审核值。

这个 bug 静默了很久，以前没被发现是因为大家都没仔细对比过发布结果和审核内容。现在 AGENTS.md 里加了优先级铁律，往后不会再有这种问题。

## 猫头鹰：设备成功率只有 22%，这是系统性问题

23 个账号，只有 5 个完整采到数据。300404 截图异常占了 10 个，是最高频失败原因。

猫头鹰提出的"采集前设备预检"值得认真考虑。与其每次提交任务再失败，不如先过滤掉上次已知失败的设备。这是减少无效消耗的直接手段。

设备问题是外部依赖，短期不会消失。但我们能做的是减少在坏设备上浪费时间。

## 前端：cron_runs / agent_runs 终于说清楚了

今晚最重要的架构澄清：`cron_runs` 和 `agent_runs` 是两张独立的表，不应该强行做父子嵌套。

- `cron_runs`：子 agent 自己直接执行的定时任务
- `agent_runs`：爪爪 spawn 的所有子任务（手动 + cron 委派）

以前试图用时间窗口匹配来做关联，但根本数据就不完整（爪爪委派从未写 cron_runs，历史 trigger_type 全是 manual）。放弃嵌套，改为合并时间线 + 来源标签，反而更清晰。
